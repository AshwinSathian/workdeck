# Later

Ideas that came up while building 0.1 and are outside it. Nothing here is built. "The spec" is [`../design.md`](../design.md).

- Remove old marker files from `<git-dir>/workdeck/`. They are empty and never cleaned up; cleaning would need `find`.
- `card show <id>` for a card that exists on the base branch but not in the working tree. `card list` shows it; `show` says there is no such card. In the skill flow the base branch is checked out first, so it only happens on a stale branch.
- A cache of open pull requests so `card status` can show `review` without `--fetch`.
- Run test cases in parallel. The suite takes about a minute on macOS, nearly all of it git process start-up.
- A single Go binary with the same commands, which would also lift the native Windows limit (spec section 3).
- A tests gate that matches the words of a `Tests` line within a window of lines, for nested test names (finding 1). Rejected for 0.1: it trades false failures for false passes.
- If the post-tool-use hook's 45 ms is ever felt (finding 6): let `card` skip `git rev-parse` when it is run from a directory that holds `.git` and `workdeck.conf`, and have the hook change to the root first. Needs no new interface. After that, an offset into the transcript.
- A first card written by init from a one-paragraph description (spec section 20, question 2).
- A card file renamed between the local and the remote base branch is looked up under both names.
- Plugin eval cases for the skills. Cut from 0.1: `claude plugin eval` is built for skills the model chooses to invoke, and these four are typed by the user. Worth one probe case if the tool gains a way to run a typed skill.
- Rename commands for consistency (`card log`, `card config`, `card check scope`), keeping the old names as aliases; a man page, shell completions and `--json`.
- An approval commit for a quick card, as 0.2 makes for a planned one (design-0.2 section 10.4). A quick card is new in its own pull request, so a file added to `Touch` after the user approved the card does not show in the diff.
- `test/run.sh` prints the `skip:` lines of a case that passes. Today a case that skips looks like one that ran: `test_plugin_validates_strictly` without Claude Code, and the comparison with `card` 0.1.3 in a clone without the tag (the eleventh pass of `review-0.2.md`). Since P-18 four cases skip there, not one.
- A second case for the comparison with `card` 0.1.3, on decks no 0.1 case builds: `status --fetch` with an open pull request, a card branch whose id is not in the deck, `status_max_chars` of 0 and at the length of its note, a log line of 200 characters, and `log_dir` set. Twenty mutations of `bin/card` pass the suite there.
- `card plan` applies the title rules of a card to a row: a title that starts with a quote, `[` or `{`, or is a multi-line marker, passes `card plan` today and is refused by `card plan start` (the twelfth pass of `review-0.2.md`). The same for a `depends` that ends in a comma, which `card plan` rejects and `card plan start` accepts.
- Cases for `card new` that no test has: a title of 80 and of 81 characters, and one that starts with `'`.
- Read file names from git with `-z`, in `diff_files` and in `card plan check` together. Today a name that git quotes, one with a `"`, a backslash or a control character, matches no `Touch` entry in `card touched` or in `card plan check`, and an entry that starts with a quote can match the quoted line (the thirteenth pass of `review-0.2.md`). Changing one of the two would make the check disagree with the gate it predicts.
- `section_items` on a card file that cannot be read prints awk's own message. `card plan check` tests for it first; `card touched`, `card tests` and `card show` do not.
- The stop hook in a shallow clone whose boundary commit is on the card branch: that commit is compared with the empty tree, so a card-only commit there is counted and the turn is blocked (the fourteenth pass of `review-0.2.md`). 0.1.3 blocks there too.
- next-card's step 5 looks for a card's branch with `git branch --list "card/<id>*"`, which also lists the branch of a longer id: for `AUTH-1` it lists `card/AUTH-12-x`, and the skill can offer to resume the wrong card. `card` maps a branch to an id exactly, the id and then `-` or the end. The plan skill reads `card list` for this (the sixteenth pass of `review-0.2.md`).
- Design-0.2 section 19 names pages that have moved. What it cites on `slash-commands` is on `skills`; row 6 was found on `agent-sdk/user-input` ("Limitations") and not on `sub-agents`; row 14 has a page now, `plugins/components` ("Agents"), for the form of the name. Read on 2026-10-10 for P-13; the claims hold.
- A row title passes `card plan` and `card list` with `$(`, a backtick or `|` in it. Neither the plan skill nor handoff puts a title in a shell command as written, but a session that builds a commit message from one with `-m "..."` would run it (the sixteenth pass of `review-0.2.md`).
- Handoff on a branch whose pull request is open, a review-fixes session: step 7 names only `gh pr create`, so the body is not written again, and a file added to `Touch` while fixing review comments is not in "Changes to the card since it was approved" (the eighteenth pass of `review-0.2.md`). The plan skill has the `gh pr edit` path. Until then the measure for such a card is read with `git diff`.
- `card plan` refuses `; ` in a `spec` item. The comment `card plan start` writes joins headings with `; `, so a heading that holds one cannot be told from two. The reviewer is told to match before it splits; the check would make that unnecessary.
- A card file renamed after its approval commit shows in handoff's part as a file removed, not as a diff.
- `templates/workdeck.conf` lists `# touch_ignore = package-lock.json, *.snap` under "Defaults, shown for reference". The default is empty. The line is an example and should say so.
- Init puts the check command into `.claude/settings.json` as written. A command with a `"` or a backslash needs escaping as a JSON string, and step 5 does not say so. As in 0.1.
- `card plan new` accepts a specification inside the cards directory. With `cards/spec.md`, `card lint` then fails in 0.1.3 and in this version, `file name does not start with a card id`; with `cards/plan/spec.md`, `card plan` reads the specification as an outline and fails (the twenty-first pass of `review-0.2.md`). `card plan new` should refuse the path.
- Handoff's step 4 moves `Touch`, `Tests` and `Acceptance` into the remainder and does not name `Read`. `card new` leaves `## Read` empty, so the `card lint` that ends the step fails with `## Read has no items` until the session fills it. As in 0.1.
- README.md, the FAQ answer for a repository set up with 0.1, says "a 0.1 repository that does not use the planner works as before". Four things differ with no outline: init does not stop, the stop hook leaves out commits that change nothing outside the cards directory and finds the log from a subdirectory, the permission template has six more entries, and `card new` refuses a symbolic link (the twenty-third pass of `review-0.2.md`). The changelog names them. The README sentence is P-24's to rewrite, or a quick card's.
- `card new`'s refusal of a symbolic link is in the changelog and in neither README.md nor `docs/reference.md`.
- Not run in the hand runs of P-21, and owned by no card: init on a repository that is up to date (whether each of the four steps ends in one line, and what step 9 proposes again after a no), on a new repository (whether `card conf` in step 4 is prompted before step 5 adds `Bash(card *)`), after the check command changed since the settings file was written, and with many `.snap` files or a marked file offered by a name with a letter outside ASCII. From F-03, and also not run: a protocol section that differs and holds a fenced code block with a `# ` line, one with a fence that is never closed, and an answer to the fourth step that is neither a yes nor a no.
- The plan reviewer runs `git hash-object` on the specification, and the hand runs' reviewers chained it with other commands; each waited. F-02 tells the reviewer not to. If it still does, an allow entry for `git hash-object *` is the other way.
- The plan skill's step 7 has a decision of the user written into the outline as a `does` or a `not` line (F-02). A `not` line is defined in three places as naming the row that owns the work: "Cutting rows" of `skills/plan/SKILL.md`, `docs/reference.md` and section 5 of `docs/design-0.2.md`. The plan reviewer's step 3 checks that row, and `card plan start` copies every `not` line into the card's `Out of scope`. A decision that names no row fits none of these. Either the outline gets a place for a decision, or the three say that a `not` line may hold one (the twenty-sixth pass of `review-0.2.md`).
- The table of the plan skill's step 8 shows the `does` lines and not the `not` lines, so a `not` line the session wrote for a decision is first seen by the user in the pull request's diff.
- The plan skill's steps 7 and 9 say "both runs", and an outline edited in step 8 is reviewed up to twice more. As before F-02. `docs/design-0.2.md`, section 10.1, and three tests hold the words.
- Init's line "Then do step 10", for a repository that is already set up, names step 10's three next steps: `/workdeck:quick`, `card new` and `/workdeck:plan <spec path>` (F-03). A test holds the line and none compares it with step 10, so a next step added to step 10 has to be added to the line by hand. The checksum of the skill shows that step 10 changed, and not that the line is behind (the twenty-seventh pass of `review-0.2.md`).
- Init's fourth step for a repository that is already set up offers a yes or a no for the protocol section and does not say what to do with another answer, such as "add only the two lines". A session may do what the user asks. F-03 left it: the fault seen was the offer, not the request (the twenty-seventh pass of `review-0.2.md`).
- The sentence on the Write and Edit tools (F-04) is in the next-card, quick, plan and handoff skills and in `reference/implement.md`. Init and the protocol section, `templates/claude-md-section.md`, do not have it. Init copies, appends and merges, `.claude/settings.json` among its files, and ran in auto mode in the hand run, so nothing was seen (the twenty-eighth pass of `review-0.2.md`).
- That sentence says "write and change". The steps also delete a file (the body of a pull request, a card after a no, an outline after a no) and restore one with `git checkout -- <outline>`, and nothing says that a delete is a command of its own. The hand runs chained `rm -f` with the body file and `gh pr create` in three sessions; whether it was the cause of the denied push is not known.
- With the body of a pull request in that sentence's list, two paths are harder. A resumed plan run starts its body from `gh pr view <number> --json body`, and must now copy it through the Write tool, where a line of a finding can be lost or reworded. And the body file is in the working tree: where handoff stops after the push because `gh` is missing, it neither deletes the file nor prints the body, as the plan skill does, and the next `/workdeck:next-card` stops on a dirty tree. Neither path was run.

Making it whole needs the log written after the commit that holds it, or the fields filled in by a later command. P-23 lists the fault as open.
